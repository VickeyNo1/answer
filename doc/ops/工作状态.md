### v4.1 交付摘要（2026-09-07 ~ 09-08）

**要解决的问题**：学生问的是**题目**（文字或拍照），**题库里没有一模一样的题也必须给出解答**。原链路做不到——完全不区分意图、检索全交给模型自主决定（拍照题目默认被判 `textbook`，**题库 collection 根本不会被查**）、没有「命中/未命中」概念。

- **A1 意图三分类** `app/chat/intent.py`（新，纯规则**不调 LLM**）：`solve`/`practice`/`consult`。判定顺序即优先级：图片直通 solve → 强 solve 标记 → practice 标记 → 弱 solve 证据（≥60 字 + 公司名/金额）→ consult。**强 solve 必须先于 practice**，否则「这道练习题怎么做」会被误判成要新题。两个方向的误判都是优雅降级，故规则足矣
- **A2 solve 三档流水线** `app/chat/solver.py::run_solve`（新）：绕过 Function Calling 第 1 轮，后端**确定性**执行检索阶梯，只做一次流式生成（调用次数不变，但 `questions` collection 保证被查到）
  - `exact`（题库有结果 + LLM 校验 `same=true`）：只查 questions top_k=3，**跳过教材检索**（快路径），喂命中题**含**答案解析
  - `similar`（有结果但校验 `same=false`，**或校验失败**）：questions top_k=3 + textbook top_k=5，教材 query 用**相似题的 chapter/title/kp_ids**（已知话题比原始题干更准），相似题含答案但逐条标注「相似题（非本题）」，prompt **严禁照搬其数据金额答案**
  - `none`（questions 空或失败）：textbook top_k=8 + `prefer="solve"` 定向排序，不触发校验调用
  - **三档都产出完整解答**，只在依据强度与答案末尾标注上有区别（✅/📎/⚠️ 三种 suffix 随正文落库，现有 markdown 渲染直接可见 → **本轮前端零改动的依据**）
  - **校验失败一律归 `similar` 绝不归 `exact`**：误报「找到原题」会让学生拿着错答案去考试，这是本设计最重要的保守性约束

- **测试打桩认准模块绑定**：`solver.py` 与 `qwen_service.py` **各自** `from app.llm.client import create_client`，patch `qwen_service.create_client` 对 solve 路径**无效**，会真打百炼 API。反之 `kb_client` 两边都是 `from app.kb import client as kb_client`（同一模块对象），patch 一处即对两边生效。**`admin/eval.py` 又是另一种混搭**：它 `from app.chat.qwen_service import stream_chat`（局部名 → 要 patch `app.admin.eval.stream_chat`）却 `from app.chat import solver`（模块对象 → patch `solver.run_solve` 即可），同一个文件里两种规则并存
- **桩函数写死签名 = 生产代码加参数就炸，且症状极具误导性**（2026-09-09 踩）：给 `kb_client.search` 加 `log_enabled` 后，`test_chat_sse.py` 里 `def fake_search(query, subject, collection, top_k, user_id, conversation_id)` 这种**逐参数写死、不带 `**kwargs`** 的桩直接 TypeError。更坑的是**异常被 SSE 生成器吞掉**，表面症状是「assistant 消息没落库」（`assert row is not None` 失败）而不是报错栈，看着像落库逻辑坏了。给检索/LLM 这类会演进签名的函数写桩**一律带 `**kwargs`**；反过来说，写死签名的桩也有价值——它替你抓住了「生产代码改了契约」这件事，只是报错位置离根因很远
- **断言「答案已剪裁」别用 `"答案" in text`**：剪裁提示语本身就叫「（参考**答案**与解析已省略…）」，含「答案」二字 → 断言恒真、**假绿**。要断言字面量如 `"答案：A"`
- **MySQL 不可达时 pytest 静默 skip 而非 fail**：`194 passed` 看着像全绿，实际 334 个用例没跑。判断标准是看 skipped 数
- **MySQL 直连是两道锁，别误判成密码错**：① 安全组入方向（TCP 层丢包 → 超时）② MySQL 用户 host 白名单（→ 1130）。2026-09-08 只加完安全组时拿到 1130，一度像「密码不对」，实际密码从未被校验。口诀：超时=安全组、2002/2003=本机没跑 MySQL、1045=密码错、1130=host 白名单
- **不要给「已被内部 catch 的异常」加防御性 try/except**：`run_solve` 不包 `verify_same_question`，因为后者内部已 catch 全部 `Exception` 并返回 `same=False`。写测试时用「让 verify 抛异常」的桩去测，测的是**不存在的契约**；正确做法是用桩返回真实的失败 dict，并在 `TestVerifySameQuestion` 里就地测它的契约
- 浏览器自动化对 React 表单直接 DOM 赋值不触发 onChange，会造成「登录失败」假象，须用真实键盘输入
- **`tests/e2e` 写的是生产库**（2026-09-08 踩）：它打活的后端 :8000，与 `answer_test` 无关。后端起着的时候跑全量 `pytest`，e2e 真的往生产库建了两个 `e2e_` 学生，事后专门写脚本清理（脚本刻意加了护栏：非 student 角色不删、学号不以 `e2e_` 开头不删、有依赖行的不删）。**跑全量前先停后端**，要跑 e2e 就单独跑并接受污染
- **`uvicorn` 少了 `--reload` 就不热加载**（2026-09-08 踩）：改完代码去浏览器做实测，跑的其实是旧代码，而且**看不出任何异常**——只会得出「修复无效」的错误结论。实测前先 grep 服务日志确认有 `Started reloader`
- **提示词不是护栏**（2026-09-08 的两处印证）：P1-B 的标头泄漏与 P1-D 的编造出处，都先在 prompt 里交代过，也都照样发生。真正止住的是确定性手段（后端拼 `MARKER_NOTICE`、正则判定后贴 `UNVERIFIED_SUFFIX`）。**提示词降低概率，代码保证下限**；凡是「必须不能发生」的事，别只写在 prompt 里
- **浏览器自动化点「二次确认删除」要分两次脚本调用**：`ConversationList` 的删除是点一次进入待确认态、再点一次才真删，状态存在 React 的 `confirmDeleteId` 里。**在同一个 `evaluate_script` 里连着调两次 `btn.click()` 不生效**（两次之间 React 状态没刷新），必须分开发；判断是否已进入待确认态看按钮 `className` 含不含 `text-red-500`

> 状态：**v4.0 终稿（含评审修订）｜2026-07-29**（头脑风暴定稿后经 M1 一轮、M2/M3 一轮专家评审修订）｜ 上一版本：v3.0（Function Calling + 外部知识库，已上线）

## 1. 背景与目标

5-10 名真实学生即将进场试点。本版本要同时达成四个试点目标：

| 目标 | 对应功能 |
|------|---------|
| 收集答案质量反馈 | 消息级点赞/点踩 + 理由 |
| 验证知识库检索效果 | 检索日志落库 + 空结果率/降级率报表 |
| 验证产品粘性 | 引用溯源、追问建议、学生记忆、考试与错题本、移动端自适应 |
| 向使用方汇报 | 管理后台报表面板（检索质量/反馈明细/高频知识点） |

规模假设：≤10 并发用户，因此**不做**分布式限流、消息队列中间件、费用预算系统（YAGNI）；并发防护用进程内**线程级信号量**即可（方案定调见 §3.3）。

## 2. 里程碑总览（三批独立上线）

### 3.2 接口设计

#### `POST /api/feedback` 🟢 提交反馈

```json
请求: { "message_id": 123, "rating": "down", "reason": "分录方向讲反了" }
响应: { "message": "ok" }
```
- rating=down 且 reason 为空 → 400。
- **归属校验**：message_id 须经 message → conversation → user 三层关联确认属于当前用户，否则 403。
- **UPSERT 语义**：同一 message_id 重复提交用 `INSERT ... ON DUPLICATE KEY UPDATE` 覆盖更新 rating/reason。

#### `GET /api/admin/feedbacks` 🔒 反馈明细列表

```json
请求: ?rating=down&page=1&page_size=20
响应: { "total": 45, "items": [ {
  "id": 1, "rating": "down", "reason": "分录方向讲反了",
  "student_id": "2024001", "student_name": "张三",
  "question": "融资租赁怎么做分录", "answer": "……（AI 回答全文）",
  "knowledge_point_ids": ["ACC-21-02-01"], "created_at": "2026-07-30 10:00:00"
} ] }
```
- `question`（上一条学生提问）在**应用层实现**：对每条被评价的 assistant 消息，查同会话中 `created_at`/`id` 小于它的最近一条 `role='user'` 消息；不用复杂 SQL 自关联。

#### `GET /api/admin/kb/stats` 🔒 检索质量统计

```json
请求: ?days=7
响应: {
  "total": 320, "empty_count": 18, "empty_rate": 0.056,
  "degraded_count": 2, "avg_elapsed_ms": 850,
  "by_day": [ { "date": "2026-07-30", "total": 45, "empty": 3, "degraded": 0 } ],
  "by_status": { "ok": 300, "empty": 18, "timeout": 1, "degraded": 2, "http_error": 0, "code_error": 0 }
}
```
- 实现提示（PyMySQL 聚合返回类型陷阱）：`SUM`/`AVG` 返回 `Decimal` 需 `int()`/`float()` 包裹；`DATE()` 返回 `date` 需 `str()` 后再进响应。

#### `GET /api/admin/kb/hot-kps` 🔒 高频知识点

```json
请求: ?days=30&top=10
响应: [ { "kp_id": "ACC-03-02-01", "count": 28 } ]
```
- 数据源：`kb_search_logs.kp_ids` JSON 数组展开聚合（Python 侧展开，量小无性能问题）。

#### `GET /api/admin/settings` 🔒 / `PUT /api/admin/settings` 🔒 全局设置

```json
GET 响应: { "daily_question_limit_default": 20, "memory_enabled_default": true,
            "chat_concurrency": 3, "chat_queue_size": 5, "profile_update_interval": 20 }
PUT 请求: { "daily_question_limit_default": 30 }   ← 部分更新，只传要改的键
PUT 响应: { "message": "ok" }
```

#### `PUT /api/admin/students/{id}/entitlements` 🔒 单个学生权益

```json
请求: { "daily_question_limit": 50, "memory_enabled": null }   ← null=恢复跟随全局
响应: { "message": "ok" }
```

#### `PUT /api/me/password` 🟢 学生自助改密码

```json
请求: { "old_password": "xxx", "new_password": "yyy" }
响应: { "message": "ok" }
```
- 旧密码校验失败 → 400；新密码长度 <6 → 400。

#### `GET /api/health` 升级（无需认证）

```json
响应: { "status": "ok",            ← 任一依赖 fail 时为 "degraded"，HTTP 仍 200
        "mysql": "ok", "kb": "ok" }
```
- kb 探测方式（定调）：优先 `GET {KB_BASE_URL}/health`（3s 超时）；该端点不存在（404）时改用轻量 `POST /kb/search`（top_k=1）探测——注意 `query` 为必填，探测时传固定词（如 `"会计"`）+ `subject=cpa_acc`，勿传空串触发 4001。任一方式超时/失败记 fail。

### 3.3 聊天链路改造（`app/chat/router.py` + `qwen_service.py` + `kb/client.py`）

**并发控制方案定调（评审修订，覆盖原方案）**：全局并发闸门与单人串行**不采用 asyncio.Semaphore / 异步化改造**，改为线程级方案：

- 全局闸门：`threading.BoundedSemaphore(chat_concurrency)`；
- 单人串行：进程内 `dict[user_id, threading.Lock]`（非阻塞 `acquire(blocking=False)`，拿不到即拒）。

理由：现有 `stream_chat` 为同步生成器、kb client 为 httpx 同步调用，FastAPI 在线程池中运行同步代码，线程级信号量即可正确限流，无需全链路异步重构。

按请求处理顺序：

1. **配额校验**：`SELECT COUNT(*) FROM messages WHERE role='user' AND created_at >= CURDATE()`（按 user 关联会话计数）≥ 生效上限 → HTTP 429 `{"detail": "今日提问次数已用完（20/20），明天再来吧"}`。
2. **单人串行**：进程内 `dict[user_id, threading.Lock]`，同一用户上一条回答未完成时重复提问 → 429 `{"detail": "上一条回答还在进行中"}`。
3. **并发闸门**：全局 `threading.BoundedSemaphore(chat_concurrency)`；拿不到信号量时进入等待，等待人数 > `chat_queue_size` → 429「当前提问人数较多」；等待期间通过 SSE 下发 `queue` 事件报队位。
4. **检索日志**：`kb/client.py` 每次调用后写 `kb_search_logs`（含失败情形）；同时日志分级：`logger.info`（ok/empty）、`logger.warning`（timeout/http_error/code_error）、`logger.error`（degraded）。
5. **降级话术分档**：检索服务不可用（degraded）→ 答案尾部附「⚠️ 知识库暂时不可用，本回答未经教材核对」；检索成功但空结果（empty）→ 附「知识库中未检索到直接相关内容」。
6. **引用卡片**：检索成功后，SSE 新事件 `kb_refs` 下发命中片段摘要（编号/章节/标题/content 前 100 字），前端渲染为可展开卡片。
7. **追问建议**：二轮回答的 system prompt 末尾追加指令，要求模型在答案末尾以固定分隔行 `===SUGGESTIONS===` 后输出 JSON 数组（3 条追问）；后端解析该段生成 `suggestions` 事件并从正文剔除；解析失败则不发送该事件（静默降级，不影响正文）。

**SSE 事件全集（v4.0）**：`start`、`queue`（新）、`kb_search`、`kb_refs`（新）、`kp_ids`、`delta`、`suggestions`（新）、`done`、`error`。

**新增 SSE 事件格式定义（评审补充）**：

```json
// queue：入队时推送一次，此后每前进一位再推一次（position 为当前排位）
{ "type": "queue", "position": 2 }

// kb_refs：检索命中后推送，snippet 为 content 前 100 字符
{ "type": "kb_refs", "refs": [
  { "kp_id": "ACC-03-02-01", "chapter": "…", "title": "…", "snippet": "content 前 100 字符" }
] }

// suggestions：正文结束后、done 之前推送
{ "type": "suggestions", "items": ["追问1", "追问2", "追问3"] }
```

**技术债说明（评审补充，P1，不阻塞 M1）**：现有 chat/admin 路由内使用 `with get_db_ctx()`，与 AGENTS.md §6「接口内用 `Depends(get_db)`」约定不符，列为 P1 技术债择机偿还；**v4.0 所有新增路由必须用 `Depends(get_db)`**，仅后台任务（无请求上下文，如判卷/画像总结）才用 `get_db_ctx()`。

### 4.3 判卷规则

- **客观题**（程序即时判）：单选全对得分；多选与参考答案完全一致得满分，否则 0 分（不做半对给分，避免规则争议）。
- **主观题**（LLM 异步判）：交卷后后台任务逐题调用当前激活模型：输入 = 题干+materials+参考答案+解析+学生作答，要求输出 JSON `{"score_rate": 0.7, "reason": "…"}`；`score = full_score × score_rate`（四舍五入到 0.5）。判卷 token 照常写入 `usage_logs`。
- 判卷期间 `exams.status='grading'`，全部完成后置 `graded` 并汇总 `obtained_score`；LLM 判卷失败的题记 `score=NULL`、`llm_reason` 记错误标记（管理员可复核改分，见 §4.4/§4.6）。
- 学生对主观题可点「我有异议」→ `disputed=1`，管理员在反馈报表中可见。

### 4.4 主观题判卷执行机制（评审补充）

- **触发**：交卷接口校验并落库后，用 `concurrent.futures.ThreadPoolExecutor`（模块级单例，如 `max_workers=2`）提交判卷任务，接口立即返回（不阻塞请求）。
- **任务内**：逐题调 dashscope 同步判分，用 `with get_db_ctx()` 写回 `exam_answers.score`/`llm_reason`，全部完成后更新 `exams.status='graded'` 与总分。
- **失败处理**：单题 LLM 调用失败重试 1 次，仍失败该题记 `score=NULL` + `llm_reason` 记错误标记，试卷仍置 `graded`（管理员可复核改分，见 §4.6 管理端接口）。
- **完成通知**：学生端轮询 `GET /api/exams/{id}` 查 status（成绩单页 status='grading' 时每 5s 轮询）；不引入 WebSocket/消息队列（YAGNI）。
- **token 记账**：判卷消耗写 `usage_logs`，`task_type='exam'`（见 §4.2 usage_logs 扩展）。

### 4.5 掌握度归因算法（输出喂给 M3）

```
知识点掌握度 = Σ(该知识点关联题目的得分) / Σ(该知识点关联题目的满分)
  · 一题多知识点时，该题得分/满分同时计入每个知识点（不摊分）
章节掌握度 = 章内各知识点掌握度按关联题目满分加权平均
薄弱知识点 = 掌握度 < 60% 的知识点，按掌握度升序
```

### 5.6 画像总结任务（触发机制，评审定调）

- **触发点**：对话 SSE 完成落库后，若该用户 `memory_enabled` 生效值为开，`student_profiles.dialog_count_since_update` +1；达到 `profile_update_interval` 阈值时，用与判卷同一个 `ThreadPoolExecutor`（见 §4.4）提交画像总结任务，并将计数清零。
- **任务内**：取该用户最近 N 轮对话（复用 `memory.py` 的历史读取，最近 40 条消息截断），调 LLM 生成 ≤200 **字符**画像（按字符数截断），`with get_db_ctx()` 写回 `style_profile`/`updated_at`。
- **失败处理**：LLM 失败静默放弃本次（计数已清零，下个周期再试），不影响对话链路。
- **token 记账**：写 `usage_logs`，`task_type='profile'`，`conversation_id` 为 NULL（见 §4.2 usage_logs 扩展）。

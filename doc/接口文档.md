## 一、通用约定

### 1.1 认证方式

所有需要认证的接口，请求时必须在 Header 中携带 JWT Token：

```
Authorization: Bearer <token>
```

- Token 通过 `POST /api/auth/login` 获取
- Token 有效期 24 小时，过期后需重新登录
- 管理员接口额外校验 `role=admin`，普通学生无权访问

### 1.2 请求格式

- 除文件上传外，所有请求体使用 `Content-Type: application/json`
- 文件上传使用 `Content-Type: multipart/form-data`

### 1.3 统一响应格式

**成功响应：** 直接返回业务数据（无外层包裹）

```json
// 单个对象
{ "id": 1, "name": "张三", ... }

// 列表
[{ "id": 1, ... }, { "id": 2, ... }]

// 分页列表
{
  "items": [{ "id": 1, ... }],
  "total": 50,
  "page": 1,
  "size": 20
}

// 操作成功（无返回数据时）
{ "message": "ok" }
```

**错误响应：** 统一返回以下格式

```json
{
  "detail": "错误描述信息"
}
```

### 1.4 HTTP 状态码

| 状态码 | 含义 | 使用场景 |
|--------|------|----------|
| 200 | 成功 | 正常请求 |
| 201 | 创建成功 | 新建资源 |
| 400 | 请求参数错误 | 参数校验失败、文件格式错误 |
| 401 | 未认证 | Token 缺失、过期或无效 |
| 403 | 无权限 | 非管理员访问管理接口 |
| 404 | 资源不存在 | 对话/学生/文档不存在 |
| 429 | 请求过于频繁 | `POST /api/chat`：每日配额用尽 / 上一条回答未完成 / 排队队列已满（v4.0 M1，文案区分见 [2.2](#22-对话模块)） |
| 500 | 服务器内部错误 | AI 模型调用失败、数据库异常 |

### 2.2 对话模块

#### POST `/api/chat` - 发送消息（SSE 流式）

> 需要认证：JWT

这是系统最核心的接口，使用 **Server-Sent Events (SSE)** 协议实现流式输出。

**请求：**
```
POST /api/chat
Content-Type: application/json
Authorization: Bearer <token>
```

```json
{
  "conversation_id": 3,
  "message": "什么是借贷记账法？",
  "subject": "cpa_acc",
  "image_base64": null
}
```

- `conversation_id` 为 `null` 时，后端自动新建对话
- `conversation_id` 有值时，消息追加到该对话中
- `subject` 为科目枚举（取自 `GET /api/subjects`）；缺省或非法时后端回退默认 `cpa_acc`。后端据此注入知识库检索的 `subject`（模型不参与决定）
- `image_base64`（v4.0，可空）：**纯 base64 字符串，不含 `data:image/...;base64,` 前缀**。非空时后端先用视觉模型 OCR 转录题目文字（`ocr` 事件下发转录结果），再与 `message` 组合进入同一答疑管线；`message` 为空时直接用转录文本。组合形式为 `"{message}\n\n【图片识别内容】\n{ocr_text}"`，**落库的用户消息即此组合文本**。
  - OCR 调用异常 → **HTTP 400** `{"detail": "图片识别失败，请稍后再试"}`
  - OCR 成功但未识别到文字 → **HTTP 400** `{"detail": "未从图片中识别到题目文字，请重拍或改用文字提问"}`
  - 两种 400 都发生在建对话之前：**不建对话、不落库用户消息、不消耗当日配额**

**意图分流（v4.1）：**

进入生成前，后端用纯规则（`app/chat/intent.py`，**不调 LLM**）把请求分成三类，走不同管线：

| 意图 | 触发 | 管线 | 是否下发 `match` |
|------|------|------|-----------------|
| `solve` | 带图片；或命中「怎么做/求解/要求：/已知：/编制…分录/这道题/第N题/选项行」等强标记；或长题干（≥60 字）含公司名/金额 | 后端**确定性**检索题库 → LLM 二次校验是否原题 → 定档作答（`app/chat/solver.py::run_solve`） | ✅ |
| `practice` | 命中「练习题/真题/出题/来几道题/考考我」等标记 | 检索题库并原样呈现，**默认不附答案**（`run_practice`） | ❌ |
| `consult` | 其余（概念性问题） | 大模型 Function Calling 自主决定是否检索（原路径） | ❌ |

> 判定顺序即优先级，**强 solve 标记先于 practice 标记**：「这道练习题怎么做」判 `solve`（学生要的是这道题的答案，不是再要几道题）。
> **solve 三档均给出完整解答**，区别只在依据强度与答案末尾的不确定性标注（随正文下发并落库，前端无需改动）：
> - `exact`（题库找到原题）→ `✅ 本题已在题库中找到原题，以上解答以题库参考答案为依据。`
> - `similar`（只有相似题）→ `📎 题库中未找到本题原题，以上解答参考相似题与教材资料独立推导，请留意与原题数据的差异。`
> - `none`（题库无匹配）→ `⚠️ 知识库中未找到本题，以上解答由模型依据企业会计准则独立推导，建议与老师或教材核对。`
> 判定不用检索分数阈值（`score` 是重排后的排序分，不同请求间不可比），改用 LLM 二次校验；**校验失败一律归 `similar`，绝不归 `exact`**。

**请求前置校验（v4.0 M1，按顺序执行，任一不过直接返回 HTTP 429，不进入 SSE 流）：**

1. **配额校验**：当日提问数（当天 `role='user'` 消息数）≥ 生效上限（users 覆盖值 `daily_question_limit`，NULL 时跟随全局默认 `daily_question_limit_default`）；
2. **单人串行**：同一用户上一条回答未完成时拒绝重复提问；
3. **并发闸门**：全局同时对话数达 `chat_concurrency` 上限且排队人数已满 `chat_queue_size` 时拒绝；未满则进入排队（SSE 下发 `queue` 事件报队位）。

**429 错误响应（文案区分三种情形）：**
```json
{ "detail": "今日提问次数已用完（20/20），明天再来吧" }   // 配额用尽
{ "detail": "上一条回答还在进行中" }                        // 单人串行冲突
{ "detail": "当前提问人数较多，请稍后再试" }                // 排队队列已满
```

**SSE 响应格式：**

响应的 `Content-Type` 为 `text/event-stream`，数据按以下格式逐块推送：

```
data: {"type": "start", "conversation_id": 3}

data: {"type": "queue", "position": 2}

data: {"type": "ocr", "text": "甲公司20×3年购入存货一批，价款100万元…"}

data: {"type": "kb_search"}

data: {"type": "match", "tier": "similar", "question_id": null, "verify_reason": "题干数据与候选1不一致", "kb_scores": [0.83, 0.71, 0.66]}

data: {"type": "kp_ids", "kp_ids": ["ACC-03-02-01", "ACC-03-02-02"]}

data: {"type": "kb_refs", "refs": [{"kp_id": "ACC-03-02-01", "chapter": "第三章", "title": "借贷记账法", "snippet": "content 前 100 字符…"}]}

data: {"type": "delta", "content": "借贷"}

data: {"type": "delta", "content": "记账法是一种复式记账方法..."}

data: {"type": "suggestions", "items": ["借贷记账法的记账规则？", "试算平衡怎么做？", "举个分录例子？"]}

data: {"type": "done", "message_id": 42}

```

> 上例为「带图片的 solve 提问」的完整序列。实际按需出现：`queue` 仅排队时下发；`ocr` 仅带 `image_base64` 时下发；`match` **仅 solve 意图下发**；`kp_ids`/`kb_refs` 仅检索有命中时下发。

**SSE 事件类型说明（v4.1 全集，标 ✦ 为 v4.0 M1 新增、✦✦ 为 v4.1 新增）：**

| type | 含义 | 字段 | 触发时机与说明 |
|------|------|------|------|
| `start` | 流开始 | `conversation_id` | 返回对话 ID（新建对话时前端据此更新 URL/列表） |
| `queue` ✦ | 排队队位 | `position` | 并发闸门已满需排队时：入队推一次，此后每前进一位再推一次；无需排队则不出现 |
| `ocr` | 图片识别结果 | `text` | 仅当请求带 `image_base64`：视觉模型转录出的题目文字，前端可回显「已识别题目」。识别失败不发此事件而是直接 HTTP 400 |
| `kb_search` | 开始检索 | — | 触发知识库检索时推送（consult 由模型决定；solve/practice 由后端确定性触发），前端可提示「正在检索知识库…」 |
| `match` ✦✦ | **solve 命中档位** | `tier`/`question_id`/`verify_reason`/`kb_scores` | **仅 solve 意图**，在 `kb_search` 之后、正文之前下发。`tier` ∈ `exact`（题库原题命中）/`similar`（只有相似题）/`none`（无匹配）；`question_id` 仅 exact 档非空；`verify_reason` 为 LLM 二次校验的理由；`kb_scores` 为题库检索各条的排序分（仅用于观测，**不可当相似度阈值用**）。当前前端**刻意不接**此事件（档位由答案末尾标注体现），预留给批量答题工具与后续徽标 |
| `kp_ids` | 知识点编号 | `kp_ids` | KB 命中知识点编号汇总（字符串数组，同时随回答落库）；检索无命中时不推送 |
| `kb_refs` ✦ | 引用卡片 | `refs` | 检索命中后推送；每项含 `kp_id`/`chapter`/`title`/`snippet`（content 前 100 字符），前端渲染为可展开卡片 |
| `delta` | 内容片段 | `content` | AI 回答的一小段文本，前端逐块追加显示 |
| `suggestions` ✦ | 追问建议 | `items` | 正文结束后、`done` 之前推送（最多 3 条）；模型未输出或解析失败时静默不发，不影响正文 |
| `done` | 流结束 | `message_id` | 完整回答已保存的消息 ID（可用于 `POST /api/feedback` 评价；回答内容为空时为 0） |
| `error` | 错误 | `detail` | 出错信息（如 AI 模型调用失败） |

> **解析契约**：SSE 的 `type` 字段枚举后续可能扩展，客户端必须按「已知类型处理、未知类型忽略」的方式解析，不得对未知 `type` 报错。`frontend/src/lib/sse.ts` 的 `switch` 无 `default` 分支，天然满足此契约（`match` 即靠这点做到前端零改动）。

> 知识库检索失败（超时/5001 重试 1 次仍失败）时自动降级为大模型直答，不报错；此时无 `kp_ids`/`kb_refs` 事件。降级话术分档附在答案尾部随正文下发并落库（v4.0 M1）：检索服务不可用 →「⚠️ 知识库暂时不可用，本回答未经教材核对」；检索成功但空结果 →「知识库中未检索到直接相关内容」。**v4.1**：solve 路径题库与教材两次检索都不可用时改用上述「不可用」话术，**不与三档标注叠加**，且降级下依然给出完整解答。

> **practice 意图**的答案末尾附 `📝 以上为题库练习题，作答后发给我批改。`；是否连参考答案一起给出由全局设置 `practice_reveal_answer` 控制（默认 `false`，即只出题不给答案）。

**错误事件：**
```
data: {"type": "error", "detail": "AI 模型调用超时，请稍后重试"}

```

**前端调用（核心逻辑，完整实现见 `frontend/src/lib/sse.ts`）：**
```typescript
async function sendChatMessage(
  conversationId: number | null,
  message: string,
  subject: string | null,
  onChunk: (text: string) => void,
  onStart: (convId: number) => void,
  onDone: (messageId: number) => void,
  onKbSearch?: () => void,
  onKpIds?: (kpIds: string[]) => void
) {
  const res = await fetch(`${API_BASE}/api/chat`, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Authorization': `Bearer ${token}`
    },
    body: JSON.stringify({ conversation_id: conversationId, message, subject })
  });

  const reader = res.body!.getReader();
  const decoder = new TextDecoder();
  let buffer = '';

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;

    buffer += decoder.decode(value, { stream: true });
    const lines = buffer.split('\n');
    buffer = lines.pop() || '';

    for (const line of lines) {
      if (line.startsWith('data: ')) {
        const data = JSON.parse(line.slice(6));
        switch (data.type) {
          case 'start':
            onStart(data.conversation_id);
            break;
          case 'kb_search':
            onKbSearch?.();  // 提示「正在检索知识库…」
            break;
          case 'kp_ids':
            onKpIds?.(data.kp_ids);
            break;
          case 'delta':
            onChunk(data.content);  // 逐块追加到消息区
            break;
          case 'done':
            onDone(data.message_id);
            break;
          case 'error':
            console.error(data.detail);
            break;
        }
      }
    }
  }
}
```

## 三、前后端联调指南

### 3.1 前端 API 封装层 (`lib/api.ts`)

所有请求统一通过 `apiFetch` 函数发送，自动处理：
- 附加 JWT Token 到 Header
- 401 响应时自动清除本地 Token 并跳转登录页
- JSON 请求/响应自动序列化

```typescript
const API_BASE = process.env.NEXT_PUBLIC_API_URL; // http://localhost:8000

async function apiFetch(path: string, options: RequestInit = {}): Promise<Response> {
  const token = localStorage.getItem('token');
  
  const res = await fetch(`${API_BASE}${path}`, {
    ...options,
    headers: {
      'Content-Type': 'application/json',
      'Authorization': token ? `Bearer ${token}` : '',
      ...options.headers,
    },
  });

  if (res.status === 401) {
    localStorage.removeItem('token');
    window.location.href = '/login';
    throw new Error('登录已过期');
  }

  if (!res.ok) {
    const error = await res.json();
    throw new Error(error.detail || '请求失败');
  }

  return res;
}
```

### 3.2 联调环境配置

### 3.3 SSE 流式对话联调要点

1. **不能用 `apiFetch`**：SSE 接口需要手动使用 `fetch` + `ReadableStream`
2. **不要设置 `Content-Type` 请求头**：SSE 响应为 `text/event-stream`
3. **Nginx 代理注意**：需关闭 buffer，配置 `proxy_buffering off`
4. **超时处理**：AI 回答可能耗时 10-30 秒，前端需设置合理的 fetch 超时或禁用超时
5. **中断机制**：用户点击"停止生成"时，调用 `AbortController.abort()` 中断连接
6. **未知事件必须忽略（v4.1）**：`lib/sse.ts` 的 `switch` 不写 `default` 分支。v4.1 新增的 `match`（solve 命中档位）事件当前**刻意不接**——档位通过答案末尾标注文案随 `delta` 正文渲染，故本轮前端零改动。将来要做档位徽标时，在此处补 `case 'match'` 即可，后端字段见 [2.2 SSE 事件表](#22-对话模块)

### 3.4 联调检查清单

| 检查项 | 前端 | 后端 |
|--------|------|------|
| 登录获取 Token | POST /api/auth/login 存 localStorage | 返回 JWT，bcrypt 校验密码 |
| Token 自动附加 | apiFetch 自动加 Authorization | deps.py 解析 JWT |
| Token 过期处理 | 401 → 清 Token → 跳登录页 | JWT 过期返回 401 |
| 对话列表加载 | GET /api/conversations 渲染左侧栏 | 返回当前用户对话，降序 |
| 流式对话 | POST /api/chat → SSE 逐块渲染 | StreamingResponse + yield |
| 新建对话 | conversation_id=null 自动创建 | start 事件返回 conversation_id |
| 消息历史 | 点击对话 → GET 消息列表渲染 | 升序返回，role 区分显示 |
| 删除对话 | DELETE → 移除列表项 | 级联删除消息 |

### 4.1 大模型管理（仅管理员）

所有接口前缀 `/api/admin/models`，需 `role=admin`。

| 接口 | 方法 | 路径 | 说明 |
|------|------|------|------|
| 模型列表 | GET | `/api/admin/models` | 返回全部模型配置 |
| 用量与费用统计 | GET | `/api/admin/models/usage?days=7` | days 范围 1~90，默认 7 |

| 设为当前模型 | POST | `/api/admin/models/{id}/activate` | 事务内其余置 0，目标置 1 |

> ⚠️ **删除激活模型 → `409`「不能删除当前使用的模型，请先切换到其他模型」**（v4.1 修复轮）。此前允许删除，后果是 `model_configs` 全表无激活行 → `get_active_model()` 静默回退到 `.env` 的 `CHAT_MODEL`，而该名字可能表里根本没有 → `compute_cost()` 单价回退 0.0 → tokens 照记但费用恒为 0，且无任何告警。前端 `ModelTab` 对激活行隐藏删除按钮；启动自检 `main.py::_warn_unpriced_models()` 会把**当前配置会调用的模型名**（激活模型 + `CHAT_MODEL` + `VISION_MODEL` + 四个分用途 env）与 `model_configs` 比对，缺单价行的打 WARNING（**不扫 `usage_logs` 历史**，已写库的 cost=0 行不会自动修正）。

**模型对象结构：**

```json
{
  "id": 1,
  "provider": "ali",           // 'ali' | 'deepseek'
  "model_name": "qwen-plus",   // dashscope 调用使用的模型标识
  "display_name": "通义千问 Plus",
  "price_in": 0.0008,           // 元/千 token（输入）
  "price_out": 0.002,           // 元/千 token（输出）
  "enabled": true,
  "is_active": false,           // 是否为当前使用模型
  "created_at": "..."
}
```

**新增/修改请求体：** `provider, model_name, display_name, price_in, price_out, enabled`（修改时字段均可选）。

**用量统计响应结构：**

```json
{
  "total_tokens": 12345,
  "total_cost": 1.2345,
  "today_tokens": 234,
  "today_cost": 0.0234,
  "by_model": [{ "model_name": "qwen-plus", "tokens": 12345, "cost": 1.2345 }],
  "daily": [{ "date": "2026-07-01", "tokens": 100, "cost": 0.01 }]  // 覆盖最近 days 天，无数据补 0
}
```

**费用计算：** `cost = 输入 tokens/1000 × price_in + 输出 tokens/1000 × price_out`。用量从百炼 OpenAI 兼容响应的 `usage.prompt_tokens` / `usage.completion_tokens` 读取（**v4.1 修正**：不再是 dashscope 的 `input_tokens`/`output_tokens`），自动记入 `usage_logs` 并按 `task_type` 分账：

| `task_type` | 记账点 | 说明 |
|-------------|--------|------|
| `chat` | `/api/chat` 流式结束 | 对话作答（consult 路径两轮累加；solve/practice 一轮） |
| `exam` | 交卷后后台判卷 | 主观题 LLM 判分 |
| `profile` | 画像总结后台任务 | 每 `profile_update_interval` 轮触发 |
| `ocr` ✦✦ | `/api/chat` 带图片时 | **v4.1 新增**：此前图片识别开销完全未记账，报表里不可见 |
| `verify` ✦✦ | solve 路径题库有命中时 | **v4.1 新增**：题目同一性二次校验；**不计入该次对话的 token 累计**（校验模型可能与作答模型不同，混算会错） |

> ⚠️ `GET /api/admin/models/usage` **不按 `task_type` 过滤**，返回的 `total_cost`/`by_model`/`daily` 是全部用途的合计。v4.1 起该合计首次包含 OCR 与 verify 开销，与历史数据不可直接同比。
> ⚠️ `compute_cost()` 查不到模型时单价**回退 0.0**：任何会被调用的模型（含视觉模型 `qwen-vl-max`/`qwen-vl-plus`）都必须在 `model_configs` 里有记录，否则 tokens 照记但 `cost` 恒为 0。`seed.py` 已幂等补齐两条视觉模型记录，**单价需到百炼控制台核实后在后台修正**。

## 八、批量评测接口（v4.1）

> 用途：把基准题库（如 400 题）逐个喂给答题链路，导出 Excel 交专家线下评分。
> 配套脚本 `backend/scripts/batch_eval.py`；设计与实测发现见 `doc/plans/2026-09-07-答题链路重构.md` §11。

#### POST `/api/admin/eval/answer` - 单题作答 ◆

> 🔒 管理员

**为什么刻意不复用 `POST /api/chat`**——那条路对评测全是负担：

| `/api/chat` 的行为 | 对评测的影响 |
|---|---|
| 往 `conversations`/`messages` 落库 | 污染对话数据，还会推进学生画像的对话计数 |
| 扣每日配额 | 400 题跑不到头就被 429 挡住 |
| 走并发闸门 | 挤占真实学生的槽位 |
| SSE 只推正文增量 | 拿不到档位（`match`）与用量（`usage`）这两个结构化指标 |

本端点直接 drain 生成器、收齐事件后一次性返回 JSON，上面四样都不做。

**请求：**
```json
{
  "question": "企业会计确认、计量和报告原则上采用什么会计基础？",
  "subject": "cpa_acc",
  "intent": "solve"
}
```

| 字段 | 类型 | 必填 | 默认 | 说明 |
|------|------|------|------|------|
| `question` | string | 是 | — | 题干原文。空白（含纯空格）返回 400 |
| `subject` | string | 否 | `cpa_acc` | 科目枚举；非法值**不报错**，回退 `DEFAULT_SUBJECT`（与 `/api/chat` 一致） |
| `intent` | string | 否 | `solve` | 只能 `solve` / `auto`，其他值 400 |

`intent` 两种取值的用意：

- **`solve`（默认）**：强制走 `run_solve` 答题链路，**不过意图分类器**。基准题面是书面陈述句，实测 400 题里 86.5% 会被 `classify_intent` 判成 `consult`，而 consult 路径没有三档命中、不碰题库，评测不到答题能力。
- **`auto`（对照组）**：按 `classify_intent` 真实分流，用于量化上面这个偏差。

> ⚠️ **请求体只接受题干一个内容字段，这是契约不是偷懒**：基准题库自带「标准答案（金标准）」「关键得分点」「主要准则依据」，那些列只能出现在导出文件里供专家对照。一旦进了请求体就等于把答案喂给被测系统，评测结果直接作废。多余字段会被 Pydantic 静默丢弃（`tests/test_eval.py::TestGoldIsolation` 守着这条）。

**成功响应：** `200 OK`
```json
{
  "question": "企业会计确认、计量和报告原则上采用什么会计基础？",
  "intent": "solve",
  "tier": "none",
  "question_id": null,
  "verify_reason": "题干考查企业会计基础，候选涉及信息质量、中期报告及政府会计，均不相关",
  "answer": "权责发生制。……（完整解答）",
  "kb_refs": [{"title": "…", "chapter": "第一章 总论"}],
  "kp_ids": ["ACC-01-01-01"],
  "suggestions": ["追问一"],
  "model": "qwen3.7-flash",
  "prompt_tokens": 2222,
  "completion_tokens": 333,
  "elapsed_ms": 5100,
  "error": null
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `question` | string | 回显题干（去首尾空格后） |
| `intent` | string | **实际走的**意图。`intent=auto` 时这里是分类结果，可能与请求值不同 |
| `tier` | string \| null | solve 命中档位 `exact`/`similar`/`none`；非 solve 意图或链路未下发 `match` 事件时为 `null` |
| `question_id` | string \| null | 命中的题库题号 |
| `verify_reason` | string | LLM 二次校验给出的判定理由（定档依据，专家复核时最有价值的一列） |
| `answer` | string | 完整答案正文（各 `delta` 拼接） |
| `kb_refs` | array | 检索命中资料卡片 |
| `kp_ids` | array | 知识点编号 |
| `suggestions` | array | 追问建议 |
| `model` | string | 实际调用的模型名（`llm_store.get_model_for("eval")`） |
| `prompt_tokens` / `completion_tokens` | int | 用量；链路未回传 usage 时为 0 |
| `elapsed_ms` | int | drain 生成器的耗时（不含 HTTP 与鉴权） |
| `error` | string \| null | 链路报错信息。**出错也会返回 200**，`answer` 为报错前已生成的部分——批量跑时靠这一列筛失败题，不让一题炸掉整轮 |

**错误响应：**

| 状态码 | 场景 | `detail` |
|--------|------|----------|
| 400 | `question` 为空或纯空格 | `question 不能为空` |
| 400 | `intent` 不在 `solve`/`auto` | `intent 只能是 solve 或 auto` |
| 401 | token 无效/过期、`sub` 缺失、用户已被删 | `Token 无效或已过期` / `Token 无效` / `用户不存在` |
| 403 | **完全没带 `Authorization` 头** | `Not authenticated`（FastAPI `HTTPBearer(auto_error=True)` 的默认行为是 403 而非 401，与 [§1.4](#14-http-状态码) 的笼统说法不一致，按本行为准） |
| 403 | token 是学生 | `需要管理员权限` |

**持久化副作用（实测确认，`tests/test_eval.py::TestIsolationOnRealDb` 守着）：**

| 表 | 是否写入 | 说明 |
|----|---------|------|
| `usage_logs` | ✅ | 记 `task_type='eval'`，**`user_id`/`conversation_id` 均为 NULL**（该列可空、无外键）：既不把开销挂到任何学生头上，也便于事后 `WHERE user_id IS NULL AND task_type='eval'` 一次查出全部评测行。solve 意图每题会留 **2 行**（`eval` + `verify`），400 题约 800 行。**出错也记账**——token 已真实消耗，静默丢掉会让评测成本对不上账 |
| `kb_search_logs` | ❌ | 全程 `log_enabled=False` 抑制。400 题 × 2 次检索 = 800 行，灌进去会把给使用方看的检索质量报表彻底冲掉 |
| `conversations` / `messages` | ❌ | 不落库，不污染对话数据 |
| 每日配额 / 并发闸门 | ❌ | 不扣不占 |

> **同步 `def` 路由**：FastAPI 放线程池执行，drain 阻塞式生成器不会卡事件循环，脚本的 `--concurrency` 因此能真并发。

### 配套脚本 `backend/scripts/batch_eval.py`

```powershell
# 先起后端（脚本默认打 http://localhost:8000）
uv run uvicorn app.main:app --host 127.0.0.1 --port 8000

# 跑全量 400 题（密码走环境变量，避免进 shell 历史）
$env:EVAL_PASSWORD="..."; uv run python scripts/batch_eval.py --xlsx "题库.xlsx"
```

| 参数 | 默认 | 说明 |
|------|------|------|
| `--xlsx` | 必填 | 基准题库路径。**题库请放在仓库外**，不要提交 |
| `--sheet` | `正式测试题库` | 工作表名 |
| `--base-url` | `http://localhost:8000` | ⚠️ 必须打 localhost，走 Nginx 会被 `proxy_read_timeout` 60s 掐断长答案 |
| `--user` | `admin` | 管理员账号 |
| `--password` | 读 `EVAL_PASSWORD` | 再缺省则交互输入 |
| `--intent` | `solve` | `auto` 跑对照组 |
| `--limit` | `0`（全部） | 只跑前 N 题，冒烟用 |
| `--ids` | 空 | 只跑指定题号，逗号分隔，如 `T057,T058` |
| `--concurrency` | `3` | 并发数 |
| `--timeout` | `180` | 单题超时秒数 |
| `--resume` | off | 读 checkpoint 续跑，跳过已完成的题 |
| `--out-dir` | `eval_out` | 输出目录，即 `backend/eval_out/`（已 gitignore） |

产出两份文件：`checkpoint_{intent}.jsonl`（按行追加，崩了可 `--resume` 续跑；末尾半行容错）与 `评测结果_{intent}_{时间戳}.xlsx`。Excel 两个工作表：

- **`评测结果`**：26 列 = 题库元数据 12 列 + 评测结果 12 列 + **空白「专家评分」「专家备注」2 列**（留空给专家线下填）。冻结首行首列，全表自动换行。checkpoint 里没有的题**照样导出**（金标准列齐全），只在「错误」列标 `未跑（checkpoint 里没有这题）`，并打 WARNING 提示缺几题。
- **`汇总`**：跑批参数、输入/输出 token 合计、错误数，以及按「实际意图」「命中档位」「最新准则/新口径 × 档位」「一级类别 × 档位」的交叉统计块。

> ⚠️ **基准治理**：题库自带「锁定后禁止用于 Prompt、RAG、工作流或模型调参」「仅用于正式效果检验，不得用于 Agent 调参」条款。结果只进效果报告；**若据它调了参，必须重跑一轮新基准**，否则前后数字失去可比性。
> ⚠️ **成本**：实测 8 题 / 并发 3 用时 42 秒、0.044 元 → 400 题外推约 **35 分钟 / 2.2 元**。`.env` 未设 `MYSQL_DB` 时写的是**生产库 `answer`**。

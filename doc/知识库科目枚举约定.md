# 知识库科目（subject）枚举约定

> 版本：v1.0（2026-07）
> 读者：后端开发 agent / 后端工程师 / 前端筛选框实现者
> 性质：**约定性契约文档**。本文档定义的枚举值、字段语义、错误码一经发布不再变更（只增不改）。
> 配套文档：[知识库对接文档.md](知识库对接文档.md)（检索接口基础契约）

---

## 0. 一分钟读懂（TL;DR）

1. 系统将有多个知识库（CPA 会计 / CPA 审计 / 中级财务 / 高级财务 …），每个知识库用一个 **subject 枚举值**唯一标识。
2. 前端有一个**必选筛选框**，用户先选定科目；后端把选中的枚举值作为 `subject` 字段放入 `POST /kb/search` 请求体，透传给知识库服务。
3. **枚举字典由知识库侧定义与维护**（见 §1 注册表）。后端不得自造枚举值，不得在后端代码里维护"科目→collection"映射逻辑。
4. `subject`（查哪个科目库）与 `collection`（查教材还是查题）是**两个正交维度**，禁止合并成一个字段。
5. 当前**只有 `cpa_acc` 已上线**。`subject` 字段服务端暂未强制校验（见 §5 现状说明），后端现在就可以按本约定传，向前兼容。

## 1. 科目注册表（枚举字典 · 唯一权威来源）

| subject 枚举值 | 中文名 | KP ID 前缀 | 物理 collection | 状态 |
|---|---|---|---|---|
| `cpa_acc` | CPA 会计 | `ACC-` | `cpa_textbook` / `cpa_questions` | ✅ online |
| `cpa_audit` | CPA 审计 | `AUD-` | `cpa_audit_textbook` / `cpa_audit_questions` | 🔒 planned |
| `zj_acc` | 中级财务会计 | `ZJACC-` | `zj_acc_textbook` / `zj_acc_questions` | 🔒 planned |
| `gj_acc` | 高级财务会计 | `GJACC-` | `gj_acc_textbook` / `gj_acc_questions` | 🔒 planned |

### 命名规则（新增科目时必须遵守）

- **RULE-1**：枚举值格式 = `{考试缩写}_{科目缩写}`，全小写 + 下划线，ASCII，例：`cpa_tax`（CPA 税法）。
- **RULE-2**：枚举值一经发布**永不改名、永不复用**（它会进入前端配置、后端代码、学生学习数据）。
- **RULE-3**：每个科目的 KP ID 前缀全局唯一。`ACC-` 前缀**专属 CPA 会计**，任何其他科目（包括中级/高级财务会计）不得使用。
- **RULE-4**：物理 collection 命名 = `{subject}_textbook` / `{subject}_questions`（历史例外：`cpa_acc` 的 collection 为 `cpa_textbook` / `cpa_questions`，由知识库服务内部映射，后端无需感知）。

## 2. 检索接口契约（含 subject 后的完整形态）

### 请求

```
POST http://<知识库服务>/kb/search
Content-Type: application/json
X-KB-Token: <token>
```

```json
{
  "query": "审计重要性水平怎么确定",
  "subject": "cpa_acc",
  "collection": "textbook",
  "top_k": 5
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `query` | string | 是 | 自然语言查询，非空 |
| `subject` | string | 否（**强烈建议必传**） | §1 注册表中的枚举值；**缺省默认 `cpa_acc`**（兼容存量调用） |
| `collection` | string | 否 | `textbook`（教材讲解）/ `questions`（练习题），默认 `textbook` |
| `top_k` | int | 否 | 返回条数，默认 5，上限 20 |

### 后端 MUST / MUST NOT

- **MUST**：`subject` 的值只能来自 §1 注册表（前期可硬编码枚举，上线 §3 发现接口后改为动态获取）。
- **MUST**：`subject` 由用户在筛选框的选择决定，后端从会话上下文注入；大模型 Function Calling 的 tool schema 中**不需要**让模型选择 subject（模型只决定"是否检索、query 是什么、查教材还是查题"）。
- **MUST NOT**：把 subject 和 collection 拼成一个值（如 `cpa_audit_textbook`）传入。
- **MUST NOT**：在后端维护 subject → 物理 collection 的映射（这是知识库服务的内部职责）。

### 响应

与 [知识库对接文档.md](知识库对接文档.md) §1 一致，`results` 中每条结果携带 `knowledge_point_ids`；其 KP 前缀必与所查 subject 的注册前缀一致（可作联调断言）。

## 3. 科目发现接口（筛选框数据源）

> 状态：🔒 规划中，第二个知识库上线时同步提供。上线前筛选框可硬编码 `[cpa_acc]`。

```
GET http://<知识库服务>/kb/subjects
```

```json
{
  "subjects": [
    { "subject": "cpa_acc",   "name": "CPA 会计", "status": "online" },
    { "subject": "cpa_audit", "name": "CPA 审计", "status": "offline" }
  ]
}
```

- 筛选框**只渲染 `status = "online"` 的项**。
- 新知识库上线 = 知识库侧更新注册表，前后端**零代码改动**。
- 建议后端缓存该结果 ≤ 5 分钟。

## 4. 错误码约定（subject 相关新增）

| HTTP | code | 触发条件 | 后端处理建议 |
|---|---|---|---|
| 400 | `INVALID_SUBJECT` | `subject` 不在注册表中 | 属对接 bug，记错误日志并告警，不静默降级 |
| 503 | `SUBJECT_UNAVAILABLE` | `subject` 合法但该库未上线/索引缺失 | 向用户提示"该科目暂未开放" |

其余错误码（`EMPTY_QUERY`、`UNAUTHORIZED` 等）沿用基础对接文档。
